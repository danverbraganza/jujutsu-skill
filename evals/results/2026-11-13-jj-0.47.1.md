# jj 0.47.1, with the conditional skill description

Run on 2026-11-13 with Harbor 0.25.0, on jj 0.47.1 only, the latest release. The agent is Claude Code
2.1.323 with `claude-sonnet-5-5`, 3 trials per scenario, 8 at a time, with the skill as of `c7da4ce`.
That skill says it is tested with 0.47.1, and its frontmatter description triggers on a `.jj` directory
or a mention of jj, where the earlier description demanded activation before any VCS operation. Harbor
passed no `--max-turns`, so the task's 900 s agent timeout was the only limit. Repos are not colocated,
except in `check-out-branch-in-git`. The self-test also passes: Harbor's oracle solves, and its nop
agent fails, all 30 scenarios on 0.47.1.

**Every scenario passes on jj 0.47.1, and no failed jj call traces to a change between 0.46 and 0.47.
With the conditional description, fewer agents load the skill, and far fewer load it before touching the
repo, but every trial still passes.**

The 0.46.0 run had 29 scenarios. `check-out-branch-in-git` was added the same day and passed 3/3 with
every agent loading the skill first
([2026-11-04-check-out-branch-in-git.md](2026-11-04-check-out-branch-in-git.md)). Skill loading is
counted here as a call to the `Skill` tool for `jujutsu`.

## Skill loading

None of the 30 prompts mentions jj, so the only trigger the new description offers is the `.jj`
directory, which an agent sees only after looking at the repo. The earlier description told the agent to
activate the skill before any VCS operation.

- 76 of 90 trials loaded the skill at some point, 15 of them before their first shell command. The 15
  are spread over `fetch-and-rebase`, `move-bookmark-forward` and `start-change-on-main` (3 each), and
  `create-bookmark`, `push-new-bookmark` and `resolve-rebase-conflict` (2 each).
- None of those 15 trials ran git. All 58 trials whose first shell command ran git had not loaded the
  skill yet; the usual opening was `ls -a` together with `git status` or `git log`.
- 14 trials never loaded the skill and passed anyway: all 3 of `recover-abandoned-commit`,
  `reword-older-commit` and `squash-into-parent`, 2 each of `abandon-middle-commit` and
  `edit-earlier-commit`, and 1 of `restore-file-from-old-commit`. 4 of the run's 8 failed jj calls came
  from these 14 trials; the other 76 trials produced the remaining 4.

## Git attempts

In the 87 non-colocated trials, 55 ran at least one git command, and 55 opened with one. Every git
command was read-only: `git status` 30 times, `git log` 25, `git branch` 4, `git remote` 4, `git config`
3, `git reflog` 3, and `git rev-parse` once. Each got `fatal: not a git repository`, and the agent carried
on with jj. No agent ran a git command that changes anything. The 3 colocated `check-out-branch-in-git`
trials ran `git checkout release`, which is the task.

## Failed jj calls

- `push-undescribed-change`: `jj git push -b quick-fix --allow-new` in all 3 trials, each with the skill
  loaded. jj removed the flag in 0.42, and every 0.46 run has seen this; each agent then pushed without
  it.
- `edit-earlier-commit`: `jj new <id>` on the empty working-copy commit that jj had already abandoned
  when the agent ran `jj edit`, in 2 trials, neither of which loaded the skill. Seen in every run.
- `recover-abandoned-commit`: `jj op undo <operation-id>` in 1 trial, which had not loaded the skill.
  jj deprecated `jj op undo` in 0.33 and removed it in 0.39; the skill's `jj op restore <operation-id>`
  would have worked. The agent recovered and passed. Not seen in earlier runs.
- `resolve-rebase-conflict`: a bare `jj squash` of a described commit into a described parent opened the
  editor, the run's only editor prompt, in 1 trial. The skill warns about exactly this.
- `squash-into-parent`: `jj squash -r <id> --into <id> -u` in 1 trial without the skill. jj rejects
  `--revision` together with `--into`; that pairing takes `--from`.

## Nothing moved between 0.46 and 0.47

The 0.47.0 change the skill now documents, that `jj git fetch` and `jj git push` in non-colocated
workspaces no longer update Git's remote-tracking refs, is invisible to these scenarios:
`fetch-and-rebase` and the three push scenarios pass 12/12, with the `--allow-new` retries as their only
failed calls.
